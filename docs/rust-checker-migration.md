# Rust checker migration

Move SlopHawk's checker decisions, indexes and foreground verification commands into a shared Rust engine. Run the final daemon, CLI and MCP bridge as native binaries. Use short-lived language-tool workers for compiler facts and test execution. This gives the idle daemon a path to lower memory use and lets C# retain compiler-accurate analysis. Measure the entire process tree before switching defaults.

The baseline is SlopHawk commit `3819a66`. It ships foreground contract, probe, path and review commands, plus C# source reconciliation and project-based test selection. The clone index and Roslyn document-fact extractor are library components exercised by tests. The clone index handles whole-block exact and renamed-local matches. Near-clone search, spelling and several supplemental checks are still roadmap work. The real test runner is also gated separately from the scheduler and its fixtures. ## Language providers

Ship all four providers behind one capability contract. Each provider must cover source discovery, syntax-level checks, clone and spelling input, and revision-aware reporting. Each must demonstrate a project or module context, a test-selection and receipt workflow, and a supported scalar contract and replay fixture before the four-language release. Require explicit coverage status for each rule and target. Cross-language impact requires explicit evidence such as a binding, schema or generated interface.

## Data and process boundaries

Keep a small shared Rust crate for provider facts, rules and evidence contracts, a checker crate for analysis, and a CLI/daemon crate for orchestration. Provider-specific parsers stay behind adapters. Decode one bounded source unit at a time. Run work that needs a whole compilation or unbounded third-party allocations in a supervised, recyclable worker. Reuse one fact extraction per document and context across applicable checks. Release parser trees and source buffers when extraction ends.

Use the existing workspace identity, epoch and committed revision to bind each job. A fact batch carries provider/schema/tool version, target context, logical document ID, physical source digest, enabled capabilities and a bounded set of records. Preserve provider coordinates and map to half-open byte ranges in the original source when the mapping is exact. Test UTF-16 offsets, encoding markers, CRLF and Unicode. A terminal frame reports evaluated rules and complete, partial, unsupported, deferred, cancelled, stale or failed scope with reasons. Missing or incomplete evidence cannot satisfy a rule.

Use length-prefixed JSON over worker stdio initially. Cap frame size, records, in-flight bytes, diagnostic output, request lifetime and total job output before allocation or consumption. Apply backpressure when readers lag. Validate worker output and discard a job's staged publication if its epoch, inputs or policy changed, its terminal frame is missing, or the worker exits unsuccessfully. Commit accepted facts and invalidations together. Keep one report publisher per workspace and preserve the existing CLI, MCP, exit-code and report contracts during cutover. [Publication protocol](result-publication.md) · [Worker execution and trust](architecture.md#repository-execution)

Start from the proposed 32 MiB resident index budget per active checkout. Account for decoded pages, SQLite buffers and connection count, interned strings, queue buffers and allocation capacity. Keep separate caps for per-job scratch and per-user aggregate work. Persist compact tokens, fingerprints and postings in SQLite, page candidates from disk, and verify matches against the same revision. Evict by bytes, cap per-fingerprint fan-out, and report work deferred by limits. Replace deleted or renamed postings in the same transaction as source changes. Keep one heavy worker per user by default. Tie compiler and runner lifetime to the supervised process scope, including cancellation and profile revocation. ## Migration and rollback

1. **Freeze the baseline.** Inventory rule IDs, public commands, provider coverage and schema versions at the pinned commit. Capture representative inputs and timing/allocation evidence for C# clone indexing, foreground checks and the resident daemon. Attribute memory separately to the index, parser or compiler, reports and workers before selecting optimizations.
2. **Prove the boundary.** Port the exact and renamed-local clone index and one verification rule. Feed both implementations the same precomputed facts. Then measure the full C# flow with Roslyn extraction included. Compare pair identities, spans, ordering, exclusions, scope gaps and results after inserts, edits, renames and deletes. Exercise Python on the same fact contract before freezing the internal protocol.
3. **Port the checker set.** Move source and graph checks, test selection and classification, and the foreground command families. Compare C# results on existing fixtures and run targeted suites for Python, Rust and FluxR. Check integer overflow, negative division, deterministic candidate order and seed compatibility, malformed IL, stale output and exact replay. Add supported and nearby unsupported cases for every scalar provider. Run authorized executable work once and compare both engines against its captured receipt during shadow evaluation.
4. **Switch the default.** Start with explicit selection of the Rust engine behind the existing CLI. Promote the native daemon per validated OS once correctness, memory and latency gates pass. Quiesce the prior daemon, transfer the writer lease and validate the workspace epoch and persisted source intents before publishing. Rebuild derived caches in a versioned location. Carry forward pending intents, receipts, policy, and review records with tested schema compatibility. Keep the .NET release available for one rollback window. Exercise native-to-.NET rollback with outstanding work and worker scopes drained. If durable formats diverge, ship a tested compatible export/import path before promotion.

## RAM and release acceptance

Compare equivalent release builds on Windows and Linux using the same checkout revisions, rule settings, input order, result budgets, worker concurrency and toolchain inputs. Capture cold startup, five minutes of warm idle, cold full analysis, repeated single-file edits, a 100-file batch, branch switches, foreground probes and multiple active checkouts. Measure parsing, semantic analysis and runner phases separately and include their overlapping memory in the end-to-end peak. Use the same precomputed facts to measure engine-only gains, including for language providers with no legacy end-to-end baseline.

On Windows, sample private working set across live processes and report private commit and Job Object peak separately. On Linux, use summed PSS from `smaps_rollup` and record cgroup memory peak separately when a dedicated cgroup is available. Sample the concurrent process set and correlate with phase markers and process exits. Report sampling interval and short-worker coverage. Compare within the same OS and metric. Record median and p95 end-to-end latency, memory, outcomes, unsupported scopes, timeouts and cache activity. Use separate profile runs for attribution so profiling overhead stays out of the release comparison. [Windows process memory counters](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex2) · [Linux proc accounting](https://docs.kernel.org/filesystems/proc.html)

Proposed promotion gates are at least **30% lower warm idle private resident memory on Windows or PSS on Linux** and **30% lower peak process-tree memory during equivalent checker work**, on each target OS. Keep the existing Windows daemon target of under **80 MiB private memory** on its documented metric and the **1 second** warm reconciliation p95 target. Allow at most **10% p95 latency regression** on matched checker runs. Freeze workloads and thresholds before measuring the Rust candidate. Publish separate end-to-end results for compiler- and runner-heavy workloads even when their memory dominates. For new providers, use explicit workload budgets established before promotion.

Require deterministic result parity for the shipped C# checks after normalizing only run-specific metadata. Document and version any approved behavior changes. Verify incremental and cold-rebuild agreement, positive findings and near misses for each supported rule, explicit partial coverage, crash and cancellation recovery, stale-result rejection, execution grants and rollback of a live workspace with pending work. Enable a language only after its advertised capabilities pass their fixtures and resource limits on the release OSes.

## Imported pilots

The pretokenized clone index, edited-branch rule, foreground replay comparator, C# fact worker and Python, Rust and FluxR syntax providers are buildable components. The daemon still routes checker and test work through its existing entry points. The native provider contract, process supervision, project and runner support, remaining rule ports and default cutover are subsequent milestones.

On Windows x64 with Rust 1.99.1 and .NET SDK 10.0.201, the C# and Rust clone harnesses produced the same 46-line trace after newline normalization. The trace exercises clone identity, ordering, scope limits, a replacement, a deletion and a cold rebuild. Each release benchmark repeated five upsert, cold query, warm query, replacement and deletion steps. The candidate cap was 10,000. The Windows process sampler requested a 1 ms interval and used private working set. The sampled peak includes fixture construction and runtime startup. The median warm-query time comes from the phase timers.

| 30 documents, 64 tokens each | 5.84 MiB | 0.74 MiB | 96 µs | 65 µs |
| 600 documents, 256 tokens each | 46.65 MiB | 12.27 MiB | 5,225 µs | 1,570 µs |

The 30-document native run yielded eight OS samples. The 600-document runs yielded 242 C# and 106 Rust samples. These are single-host, engine-only observations using pretokenized documents.
