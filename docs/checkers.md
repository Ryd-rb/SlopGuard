# Checkers and test selection

## Inspection providers

Each adapter declares required inputs, supported target contexts, execution permissions, cache granularity, and cost. Publish enabled and evaluated rule IDs when the provider exposes them. Distinguish unsupported rules, suppressed rules, partial analysis and missing providers. Honor compiler options, `.editorconfig`, repository rulesets and provider-specific settings. Preserve genuine differences in rule behavior when results overlap.

| Checker | Findings and initial design |
| --- | --- |
| Source integrity | Use Roslyn syntax diagnostics for malformed code, conflict markers and invalid directives. Flag newly introduced empty catches, unfinished stubs and debug artifacts under configurable rules. Recognize generated-file headers and use an explicit generated-code policy. Mark diagnostics dependent on unresolved language options as provisional. |
| Compiler and SDK analyzers | Use the repository compiler for enabled language features, binding, nullable flow, obsolete APIs, framework and platform checks, and configured build warnings. Include analyzer and generator failures and their effect on coverage. |
| Sonar C# rules | Offer a pinned, locally installed `SonarAnalyzer.CSharp` profile. Run compatible rules with the target compilation settings and report active rule coverage. SonarQube server profiles, cross-file analysis and quality gates depend on the configured server and scan. Keep that integration optional and explicit. |
| JetBrains inspections | Run pinned InspectCode when installed, with solution/team settings and machine-readable output. Cache by solution context, pass an appropriate toolset and schedule as heavyweight work. Full interactive Rider equivalence is outside the adapter's coverage contract. |
| Formatting and API usage | Report formatting and code-style violations, unused members where resolvable, redundant constructs, unawaited tasks, resource lifetime and cancellation issues. Run format verification without editing files. Prefer built-in analyzer rules where available. |
| Reliability and performance | Check sync waits in async paths, disposable and cancellation-token ownership, lock misuse, repeated enumeration, allocation-prone APIs in declared hot paths, and unbounded caches or queues where the rule can identify them. Lead with analyzers and enforce repository-specific rules only where their scope is explicit. |
| Defensive coding | Detect hardcoded secrets without returning the values, unsafe query construction, missing validation at declared boundaries, permissive certificate validation, and logging of configured sensitive fields. Keep signature-based and semantic results labeled with their evidence. |
| Dependencies and project wiring | Inspect evaluated project references, compile inclusion, package lock and assets files. Report missing graph edges, incompatible target references, unapproved dependency additions, analyzer downgrades and stale restore inputs. Surface advisory data freshness if enabled. |
| Architectural boundaries | Check declared forbidden references, project cycles, layering constraints and duplicate public contracts. Compare public API against a baseline and report changes with project and target context. |
| Agent edit integrity | Detect newly disabled or skipped tests, removed assertions, newly added broad warning suppressions, newly public members and copied placeholder bodies. Report structural evidence and confidence. Use diff context to avoid resurfacing unrelated debt. |
| Repository invariants | Provide declarative rules for forbidden APIs, required cancellation forwarding, expected DI registrations or required integration seams. Use typed symbol signatures for semantic rules and typed config for exceptions. |
| Spelling | Split PascalCase, camelCase, acronyms and snake_case in identifiers. Check comments and docs under their own policy. Exclude URLs, hashes, generated code and string literals by default. Report the unknown token and bounded suggestions from a versioned local dictionary, with user and repository whitelists. |
| Test outcomes | Report passed, failed, skipped, zero discovered, build failure, adapter failure and unavailable coverage by runtime and target. Attach the failing test identity and a bounded diagnostic excerpt. Preserve first failures across explicitly requested reruns. |

Provider contracts are based on their own documentation. [Sonar C# analyzer package](https://packages.nuget.org/packages/SonarAnalyzer.CSharp), [SonarScanner workflow](https://docs.sonarsource.com/sonarqube-cloud/analyzing-source-code/scanners/sonarscanner-for-dotnet/using), [JetBrains InspectCode](https://www.jetbrains.com/help/resharper/InspectCode.html), [Microsoft package reporting](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-package-list)

## Duplication detection

Index Roslyn tokens in methods, constructors, accessors, local functions, lambdas and sufficiently large statement runs. Start with a minimum of 40 substantive tokens. Ignore comments and trivia, exclude generated files by default, and index two representations.

- **Exact token match** preserves identifiers and literal values. Report 1.0 only after comparing the token spans.
- **Renamed or edited match** normalizes local identifiers consistently within a fragment and buckets configurable literal types. Preserve operators, control flow and resolved member identities when available. Label the normalization and show whether symbol resolution was available.

Hash sliding token shingles and select sparse fingerprints via winnowing. Look up matching postings to nominate likely peers, and bound postings for common boilerplate. Refine candidate spans with bounded token alignment. Compute similarity as `2 × aligned matching tokens / (left span tokens + right span tokens)` over the selected representation. Report the score, normalized and exact matched token counts, both spans, tuning profile and whether candidate limits were reached. Start with a near-match threshold of 0.80. Calibrate using real fixtures containing overloads, generated data, repeated guard clauses, renamed copies and edited clones. Treat normalization and threshold changes as index version changes.

Update postings for changed files and remove deleted postings and affected result pairs transactionally. Recompute peers of removed or changed pairs so stale matches disappear. Prefer maximal spans and collapse nested overlapping results. Order ties by score, span size and path. Save only compact fingerprints, offsets and lookup metadata on disk. Heavy solution scans can expand limits under explicit request. Keep this checker independent of JetBrains tooling. [JetBrains dupFinder retirement](https://blog.jetbrains.com/dotnet/2021/08/12/sunsetting-dupfinder-command-line-tool/), [Winnowing paper](https://theory.stanford.edu/~aiken/publications/papers/sigmod03.pdf)

## Related test discovery and execution

Discover candidate test projects under the workspace from solution membership, evaluated project properties, project references and installed adapters. Support projects outside solutions. Group test IDs by target framework and adapter. Treat naming conventions and framework attributes as discovery hints. Obtain runnable test identities from the runner for the corresponding build, and cache them against test assembly and configuration inputs. Honor repository settings and distinguish unit projects from integration and end-to-end projects through project policy and test metadata. Surface unclassified or intentionally excluded coverage.

For each batch containing confirmed C# additions, edits, deletions or renames, select tests in this order.

1. Start from both old and new project membership and test ownership for each path. Reverse-walk project dependencies separately for each affected build context. A changed test may affect its containing class, shared fixture or entire project.
2. Run a bounded test subset only when verified impact evidence supports the filter for the current context. Static method links and previous coverage may prioritize tests. Uncertain reflection, DI, serialization, generated code, shared fixtures, global usings and broad API changes require a wider selection. A narrow run with heuristic evidence is labeled partial.
3. Fall back to all unit tests in the affected test projects if method-level evidence is incomplete or a runner cannot express the filter. When project impact is also uncertain, select the workspace’s configured unit-test group subject to the automatic run budget, and report any deferred scope. Never silently treat zero discovered tests as a pass.

Use VSTest for compatible test projects in SDK-style and classic Windows workspaces. Use Microsoft.Testing.Platform when selected by compatible projects and SDK settings. Resolve runner-specific filters and output formats through adapters for xUnit, NUnit and MSTest. Add explicit adapters for legacy runners when fixtures demonstrate the need. Reuse a build only when the relevant input and output graph matches, including generated sources and adapter binaries. Otherwise request the minimum necessary build and apply restore policy. [dotnet test and runner selection](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-test), [Microsoft.Testing.Platform migration](https://learn.microsoft.com/dotnet/core/testing/migrating-vstest-microsoft-testing-platform)

Startup inventory, metadata-only events and tool outputs never trigger automatic tests by themselves. Metadata changes can invalidate discovery, and a later C# batch uses refreshed discovery. MCP can request explicit tests against the current workspace even when no C# file changed. Reports identify triggering paths, selected and omitted test projects, any filters, reason for selection, toolchain, elapsed time and the source revision the results actually covered.
