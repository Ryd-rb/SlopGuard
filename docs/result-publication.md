# Current results in `.slophawk`

Every checker publishes through one daemon-owned exporter. The workspace projection is `.slophawk/results.json`, a bounded JSON document covering all enabled checkers under the shared workspace policy. Checker jobs never write this directory directly. Detailed findings, previous revisions and session-specific runs stay in the bounded user cache and are queried through MCP. Treat `.slophawk/` as generated output and exclude it from watching, indexing, tests and version control.

## Report attribution

The document header includes the schema version, canonical workspace identity, daemon incarnation, publication epoch, committed workspace revision, configuration revision, projection revision and Git context. Advance the projection revision when displayed coverage, results or marks change, including from job completions with the same source revision. The daemon uses the observed invalidation sequence internally to gate reads and writes. The Git context includes the full symbolic branch ref or detached state, resolved HEAD commit, and any comparison base used. Record whether evaluated inputs include uncommitted edits. A commit identifies the checked-out base for live analysis. A commit-only result requires inputs verified against that commit. For a non-Git workspace or unborn branch, use a worktree identity and input fingerprint.

Each checker section includes the checker and rule versions, current state, evaluated languages and targets, and an explicit scope. Findings carry provider ID, repository-relative paths, source ranges and input fingerprints. Mark a deleted path as a deletion and identify its previous span or commit when available. Project and repository checks identify the evaluated project or commit and any related files. Imported evidence records the originating build, artifact or deployment separately. Report each checker and target with one coverage state, the reason for missing scope when applicable and an independent run outcome. Use `pending` for work waiting for evaluation or currently being evaluated, `deferred` for budget or scheduling limits, `partial` for incomplete evaluated scope, `blocked` for a prerequisite or authorization failure, `disabled` for inactive policy and `complete` for fully evaluated scope. Record projection truncation separately from checker coverage. A complete test run can contain failing tests. A failed prerequisite build blocks test coverage and points to the build output. A checker that has not completed for the current revision reports its coverage state without old findings.

## Agent status and checker reactions

The report includes stable finding IDs, status target versions and a report token. Send marks over MCP with `mark_result`. Mark the report itself, an affected path or a finding ID listed for that report. A path mark applies to the findings listed for that path at the submitted revision. Show agent marks alongside checker outcomes.

| Agent status | Daemon response |
| --- | --- |
| `acknowledged` | Record that the agent reviewed the result. |
| `fix_in_progress` | Keep the result visible until fresh evidence supersedes it. Let normal edit detection drive rechecks. |
| `recheck_requested` | Queue the applicable checkers for the marked scope. |
| `needs_analysis` | Queue deeper symbol, value-flow or provider analysis within the configured policy and budget. |
| `suspected_false_positive` | Queue a review with the supplied reason and retain the finding while it is investigated. Shared suppressions use the existing configuration path. |
| `cleanup_requested` | Revalidate the scope and remove exporter-owned results whose inputs or findings have become obsolete. Preserve current findings and source files. |

Only revalidated checker evidence resolves a finding. Store marks in the shared database, with the session, short reason, target identity and input revision. Expire them on a branch transition or when their target inputs change, and cap retained mark history. Apply idempotency and version checks in one transaction. A repeated request ID with the same payload returns the original receipt. Reject stale targets and concurrent conflicting changes with the current version for rereading. Independent targets can be marked during the same report epoch. Commit the mark and its follow-up intent together. The scheduler consumes committed intents after the transaction and resumes unfinished work on restart.

### File coordination

A report token pins the displayed target membership and projection revision. A target version changes when its underlying scoped evidence changes or a mark is accepted for that target. Accept a mark on an unchanged target from a retained projection in the same epoch, even when a disjoint target changed. A path-level mark expects the listed finding set and its evidence version together. A report-level mark expects the report's complete scope version. These marks annotate their own targets. They need no implicit writes to overlapping targets. Validate idempotent replays against the retained receipt after authenticating the requester, before checking current target state.

The exporter is the only report writer. Agents read immutable report snapshots and submit changes via MCP. They never lock or edit the report to mark it. An OS singleton guard uses a nonblocking acquisition to prevent a second daemon writer. The database writer serializes short transactions and releases them before waiting for a checker, report reader or filesystem operation outside the database. Workers return results through the scheduler and never wait for publication while holding an output resource. The report reader uses delete-compatible sharing on Windows and reads without locking the report. This removes circular file-lock dependencies from the protocol. External sharing conflicts surface as bounded publication failures with a retry and a visible status.

## Checkout and edit invalidation

1. **Establish ownership.** Take the per-worktree writer lock before reconciling or exporting files. Resolve the actual Git directory and common directory through Git so a linked worktree uses its own HEAD and index. Watch relevant Git metadata separately from source, including the symbolic ref, index and lock events and ref-store changes as applicable. Re-read Git context during reconciliation and before every publication. Treat watcher overflow, root replacement and ambiguous Git state as invalidations. [Git path resolution](https://git-scm.com/docs/git-rev-parse), [Git worktrees](https://git-scm.com/docs/git-worktree)
2. **Withdraw current output.** On any relevant event, advance the invalidation sequence and stop serving the previous report as current through MCP and the CLI. Invalidate affected work immediately and withdraw the on-disk projection through the exporter before debouncing or starting new jobs. Advance the epoch on a confirmed or ambiguous Git transition, loss of watcher continuity, root replacement or a transition lease. Ordinary in-epoch input changes use the invalidation sequence and committed revision. Switching branches at the same commit, detaching HEAD, changing the checked-out commit, and a same-branch reset or restore that changes inputs all invalidate the applicable output. Any event that could affect the report while its scope is unknown also withdraws it. Old results held in the cache can never publish under their previous epoch.
3. **Reconcile before reopening.** Wait for applicable Git lock files to clear and the watcher to settle. Read Git context before and after input reconciliation and retry if relevant events arrive during the pass. Validate each reusable result against its current scope and digests. Use a fresh epoch even for a return to the same branch and commit. A Git change by itself does not schedule automatic tests. A confirmed C# delta can do so under the normal policy. Unstable or unreadable Git or root context keeps the projection withdrawn. A stable workspace with an unresolved source or target scope can publish partial coverage for the facts it verified.
4. **Publish one complete document.** Build the next report from a single validated snapshot of results, policy and Git context. Stage one temporary file outside `.slophawk` on the same filesystem and replace the report atomically. Recheck the incarnation, epoch, sequence, committed revision and configuration against the snapshot immediately before replacement, with the live Git and input checks appropriate to its scope. If an event races the replacement, the validated reader rejects the token and the exporter withdraws it. If replacement requires a retry, repeat validation. A sequence sampled before the scan or serialization cannot stand in for final validation. A failed write or replacement never publishes a partial report. Use a reader protocol that closes handles promptly and allows replacement where the platform requires it. [Windows file replacement](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew)

The agent skill uses a short transition barrier before Git commands it initiates that can switch or rewrite the working tree. The daemon withdraws results before acknowledging the barrier, pauses publication, then reconciles after the command exits. Use an expiring lease so a terminated agent cannot leave publication paused indefinitely. External Git commands are still detected through Git and filesystem observation. Existing Git hooks may optionally call the invalidator after a supported command. Hooks are supplemental because Git operations have different hook coverage. [Git hooks](https://git-scm.com/docs/githooks)

## Reading, recovery and limits

Use `slophawk results` or MCP to consume the projection with a freshness check. Verify the report epoch and live Git context. For worktree reports, validate the relevant input inventory and digests when watcher continuity cannot establish freshness. A dirty, unverifiable or superseded scope returns no findings as current. Direct file reads can race external editors or Git, and an abrupt exit or sharing error can leave the file on disk until recovery. Consumers that need freshness use the validated reader. On restart, withdraw any prior report before rebuilding watcher continuity. On a clean shutdown, withdraw the report before releasing the writer lock.

Start with one result file capped at 8 MiB and 2,000 finding records. Keep a summary for every checker within fixed per-checker quotas. Cap excerpts and related spans, serialize incrementally and prioritize current errors and failures within each quota. Flag truncation and report included and omitted counts, with a revision token for retrieving verified details through MCP. Always include attribution, scope and coverage status. Limit staging to one owned path per worktree and exclude that path from watching. Bound file replacement retries. Rotate nothing inside `.slophawk`. The exporter reclaims only its positively identified temporary output. If an unknown file, unexpected link, foreign writer or permission problem prevents safe cleanup, report degraded publication and leave the path untouched. Validate ownership and path containment for creation, replacement and removal.
