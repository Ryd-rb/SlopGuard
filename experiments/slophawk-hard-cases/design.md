# Hard verification cases for the SlopHawk benchmark

Product base `3cee615`. The preceding review of verification claims at `137a49c` reached 24/24 in each arm across four scored pairs. It measured a token difference at that ceiling. This design changes the review task from checking a supplied list of claims to deciding whether to ship ordinary changes whose default checks pass. The four cases below are author-side qualification cases. Keep this file, the qualification program, its output, and any label-to-dossier mapping outside the worker checkout.

## Cases and scoring oracles

Each pair changes one fact that should change the release decision while keeping the evidence that typically drives the decision intact. A correct diagnosis must name the selected release scope, identify which evidence does or does not apply to it, and explain what would change the decision. Score a worker's use of whatever evidence they can obtain. The checks in the qualification program establish the answer key.

The planning and reuse cases compile and run small SDK-style .NET projects. In planning, the runnable smoke executable and the offline planned test target are separate checks on the same project. The settlement case seeds SQLite and a typed test receipt, and the coverage case uses a synthetic Cobertura report, leased artifact and scoped source map. They exercise the current verification components directly. The positive bugs belong to the dummy consumer's release decision. The qualification does not establish support for running these scenarios through stock SlopHawk's automatic workflow.

## Additional candidates for independent dossiers

These require application replays and verified controls before enrollment. They differ in the decision and failure mechanism from the qualified probes. Prioritize them over scaling by renaming the qualified cases.

| Candidate | What makes the wrong decision look right | What a hidden replay must establish |
| --- | --- | --- |
| Bank statement normalization | A conditional project item selects rounding rules for a recovery channel. The check runs against the new channel and reports the expected total for amounts exactly divisible by 100, so a shortcut that inferred the channel from directory name appears sound. | Two amounts bracketing a rounding boundary separate the evaluated recovery implementation from the one actually exercised. A documentation-only channel rename is harmless when the evaluated target and executable stay bound. |
| Warehouse zone remapping | A generated routing table is stale because the change moved the contracted row to a new zone alias. The output's normal load succeeds and total route count matches. The old receipt says the generator ran successfully. | The replay inspects the evaluated generator input and checks whether two zones with matching counts still route an ordinary pallet differently. Accept regeneration with identical normalized routing data. |
| Invoice batch retry | Two real attempts are eligible for the same build. A failed corrected attempt arrives before a successful earlier attempt. The summary chooses the most recently received report and collapses the distinction between the brief governing the gate and the brief governing the slower attempt. | Deliver identical valid run artifacts in both arrival orders. The correct gate decision is invariant to delivery order and follows the current brief. Retrying with the same brief must allow its actual surviving completion. |
| Permit-renewal coverage | Multiple conditionally included sources map to the same collector alias. A high hit count for a shared fallback is displayed as evidence for a newly required special-case branch. A separate failing test also hit the right physical file under a different build. | Resolve the alias under the admitted build and target, prove which lines can be attributed unambiguously, and accept genuine hits on an unchanged shared mapping. A correctly labeled ambiguous line remains `Unknown`. |

## Blinded comparisons

1. Package each case as a plausible ordinary pull request with a change request, a pre-change revision, a candidate patch, representative artifacts and documented native checks. Keep the release gate in the reviewable code or configuration. Include other sensible work in the diff by building out each domain naturally. Keep the default checks green for both variants. Before using a pair, run a hidden replay against the whole dummy application that observes the intended decision and shows that the minimal repair changes it. For settlement and coverage, build the gate and replay its adapter inputs through its real entry point. Keep author programs and labels outside both worker snapshots. Rebuild packaged cases from the recorded seed and verify input hashes and denial of writes before dispatch.
2. Give both arms the same neutral request. “Review this change for release. Report concrete reasons to block it, with evidence from this checkout and a way to reproduce each finding. If the evidence leaves the decision uncertain, say which evidence is missing.” Give them the same source, pre-change base, fixtures, raw evidence, .NET tooling, interaction budget and elapsed-time ceiling. Provide the assisted arm with read-only SlopHawk verification access from the pinned build, through a thin runner if necessary. Record the exact APIs it invokes. The runner should return typed component output for a worker-selected artifact or target and avoid interpreting the release decision, counting seeded cases, or revealing which cases to inspect. Freeze and independently verify the runner before any scored run. The baseline can inspect source, compare artifacts and run the native checks.
3. Start a fresh Luna 6 High worker per arm and dossier, with no prior task history, shared chat, writable worker artifact or access to completed runs. Assign each pair the same dossier and comparable token and time limits. Randomize which arm starts first, and randomize case names and order once per pair. Mix defects, valid close neighbors, and supported `Unknown` outcomes. Avoid making every dossier balanced in a predictable way. Keep the scoring answer key outside prompts, filenames and tool output. Independently hash actual input bytes before and after each run, with stable per-entry names and hashes. Account separately for worker scratch and independently generated outputs.
4. Blind the scorer to the arm and strip arm-identifying metadata from findings. Count a defect only if the finding names the wrong release decision, cites concrete evidence on both sides of the comparison, and describes a reproducible check or a minimal correction with the right predicted effect. Boilerplate cautions or repeating a tool result do not count. Deduplicate findings by first causal divergence. Count erroneous blockers on valid neighbors separately, and adjudicate `Unknown` from the evidence present in that dossier. Score all assigned runs under the same rules. Freeze invalid-run rules such as model or effort mismatch, snapshot corruption and token telemetry missing for the cost analysis. Track all exclusions, launches and tokens consumed.

## Budget and inference

- Before scaling, run at most one blinded development pair on a dossier outside the final set. The local preflight and the packaged replay must have passed first, with no answer leakage and valid per-run telemetry. Check that both workers can complete a review with the same ceiling and neither scores at the ceiling on the development dossier. A ceiling, time exhaustion, answer leakage or bad telemetry stops scaling and calls for a new development dossier after correction. Never use the development labels or results in the final estimate.
- Freeze the final sample size, pairing and inference before dispatch. Select the smallest detection difference worth paying for and budget against plausible discordance rates. If the token budget only supports a small number of genuinely independent dossiers, report uncertainty and treat the study as exploratory. Repeating the four probes with renamed files, or counting several findings within one review as independent trials, does not increase the effective sample size.
- Primary endpoint is the difference in verified detections per paired dossier. Report paired counts, discordant findings, and uncertainty estimated over independent dossiers. Report false blocks and off-target or unverified claims alongside detections. Include attempts with zero verified findings. A narrow confidence interval around a low detection difference answers a different question from a wide interval around the same estimate.
- For each arm and dossier record total input, cached input, uncached input, output including any reasoning already in output, and total logical tokens. Use run-local telemetry, the sum across turns or the delta between cumulative snapshots, and retain the source counters. Report elapsed time and tool calls. Publish paired token differences and arm medians with ranges. Scale only on verified evidence capture and scoring headroom. Unverified savings and timeouts belong in the reported results.

## Run the author qualification

From the SlopHawk repository, choose a scratch directory that does not exist yet.

```powershell
$scratch = Join-Path ([System.IO.Path]::GetTempPath()) ('hawk-qualification-' + [guid]::NewGuid())
dotnet run --project experiments/slophawk-hard-cases/Qualification.csproj -- $scratch
```

The executable exits nonzero at the first assertion failure and preserves the scratch inputs. This is a preflight for package design. Worker difficulty, detection lift and token consumption require the blinded runs above.

Local qualification on Windows with .NET SDK 10.0.201 passed all four counterexamples and controls. The SlopHawk solution built with zero warnings and errors. Its test suite passed 376 tests and skipped two environment-dependent tests.
