# SlopHawk

For a bounded read-only workspace with a batch adapter, use the supplied runnable assembly. Read the public contracts and source in place, write cases and your answer in writable scratch, and let the checker write its own evidence in `.slophawk`. These paths support the full flagging workflow.

If the workspace lists executable public rules, start with its `check-contracts` command and save the JSON receipt. Qualification means the supplied rule reproduces the published examples. The checker then generates new inputs within the rule's domain and derives expected values from that rule. Read the qualification, summary, and, when present, the check report at `Report`. Examine any `ReplayChanges` in the summary as inconsistent observations. Build draft findings from `Result.Findings` using `Input.Operation`, `Input.Args`, `Candidate`, and `Reference`. Trace each discrepancy to the intended contract and candidate behavior. An exact replay establishes reproducibility. Check the expected value against the intended behavior before calling it a code defect. Batch the decisions through `check-retest` using the report's `Run`. Save supported, reproduced findings with exact values and the verified cause. Run the scoped review and account for unqualified operations, missing coverage, and outstanding findings.

1. Inventory the components and operations from the public contracts and routing documentation. Keep a checklist in writable scratch. If the workspace lists published examples in checker format, run them directly. Initialize the scoped review with an empty acknowledgment array and `--progress`. Its `MissingCoverage` and `Worklist` identify what to check next. Read those public contracts and implementation files together. Collect cases across the whole scope before making extra passes on any one component. Batch cases and exact retests, save verified findings as they come in, and use the worklist to choose the next component. Exercise in-contract boundaries and interactions between arguments. A smoke pass alone leaves coverage open.
2. Write cases with `Operation`, `Args`, and `Expected` derived from the public contract. Run `slophawk check <assembly.dll> <cases.json> <workspace> [run-verb [prepare-verb]]` with the documented adapter verbs. For requests without an independently established expected outcome, use `slophawk check-observe <assembly.dll> <requests.json> <workspace> [run-verb [prepare-verb]]` and omit `Expected`. Never enter a placeholder or use the candidate output as the source of an expectation. The workspace must permit writes to `.slophawk`. Each run saves `report.json`, `requests.json`, and `observed.json` under `.slophawk/checks/<run>/`. Read the files even when check exits 1. Review the coverage and outstanding findings with `slophawk check-review <workspace>`.
3. Acknowledge and test every outstanding finding. Trace the input through the public contract and candidate implementation. Run the exact input again in a separate check after independently deriving its expected outcome. Use a second boundary or neighboring case when it helps distinguish the cause. If the original expectation was wrong, retest with the corrected value. Unsupported or invalid cases leave coverage open. Replace them with supported, in-contract tests.
4. Batch exact retests with `slophawk check-retest <assembly.dll> <workspace> <run> <decisions.json> <acknowledgments.json>`. Write a JSON array with the original zero-based finding `Index` and a contract-based `Reason`. Omit `Expected` to test whether the original discrepancy reproduces. Supply `Expected` to correct an expectation when independent review establishes that the original candidate output was right. The command updates the acknowledgment file when the observed values reproduce. For a retest you ran separately, an acknowledgment can record `Run`, `Index`, `RetestRun`, `RetestIndex`, `Disposition` (`confirmed` or `corrected-expectation`), and `Reason`. Run `slophawk check-review <workspace> <acknowledgments.json>` and resolve `Outstanding` and `UnstableInputs` in `.slophawk/checks/review.json`. If review requires run selection, use `--run <run>` with the receipt for the intended assembly and adapter.
5. During a scoped audit, run `slophawk check-review <workspace> <acknowledgments.json> <scope.json> --progress` to refresh the worklist. Use a scope supplied with the workspace or derive one from the public inventory. It contains `Operations` with the names to cover and `Ordinary` with the public examples as `Operation` and `Args` entries. `MinimumOutsideOrdinary` sets how many distinct supported comparisons are required per operation and defaults to one. Use `[]` as the acknowledgment file if there are no findings yet. Address `MissingCoverage` with inputs that exercise different contract rules. Repeating a retest on identical arguments leaves coverage unchanged.
6. Continue until every component in the checklist has been reviewed and every checker finding is acknowledged and tested. Run the final review without `--progress` and check `Complete`, `Outstanding`, `MissingCoverage`, and `UnstableInputs`. Report the coverage actually exercised. For flagging requests, leave the solution unchanged and submit only reproducible supported defects with actual, expected, and cause. If a concrete blocker prevents completion, save the findings collected so far, the remaining work, and the blocker.

For subtle rules that depend on several inputs at once, write a small independent calculation from the public contract in scratch. Use it to compute expectations for a batch of valid inputs on both sides of each relevant condition. You can start from public examples with `slophawk probes plan`. Filter generated inputs against the documented constraints before using them as cases. Treat a nearby passing case as evidence about which condition caused a failing case.

When a contract defines how related inputs should behave, use `check-observe` on paired requests to test that relationship. For example, a field documented as irrelevant in a given state should have no effect when it changes by itself. Derive the exact contract outcome for a violating pair, then use `check` and a separate retest before reporting a defect.

When the workspace declares a scalar path spec and a separate writable scratch directory, run `slophawk paths build <spec> <scratch>`, then `slophawk paths plan <spec> <scratch> <Build> graph-on` and `slophawk paths check <Plan>`. Read `slophawk paths review <Review>` and account for each reproduced comparison, unstable replay and unresolved target. A structural fallback or predicted edge guides inspection. Ground every flagged discrepancy in the public rule and the original-build replay. For a controlled comparison, use `graph-off` with the same spec and build and record both reports.

For an editable checkout with daemon state available:

1. Run `slophawk start --root <checkout>`. The MCP entry point is `slophawk mcp --root <checkout>` and starts the same daemon if needed. If developing SlopHawk itself, use the local build from its README when the command is unavailable.
2. Read the daemon-owned `.slophawk/results.json` through `slophawk results --root <checkout>` or MCP `get_findings`. In 0.2 previews, check the Git context, source count and committed revision. Use `workspace_status` to inspect pending intents and scheduler state. Ready inventory means the source observations reconciled. An `awaiting_adapter` scheduler leaves test intents outstanding.
3. The watcher rechecks edits and Git changes. Use `slophawk recheck --root <checkout>` or MCP `run_checks` for an explicit refresh, then read the new revision. Treat the report as read-only. Acknowledge each reported problem and exercise an appropriate reproducing or regression test before closing it. Recheck after changes and account for new findings the same way.
4. Before reporting completion, review current evidence and run the repository's build and tests. SlopHawk delegates compiler and analyzer checks to the build.
